# Enforcer Mobile Preview — Migration (APPLIED 2026-06-11)

**Status: APPLIED to Supabase project hycuxnwskexnckedihgt.**
Applied as additive migrations `enforcer_mobile_preview_additive` and
`enforcement_events_anon_policy`. Fully reversible (see Rollback).

This document describes the *only* database changes the enforcer mobile preview
needs. Every change is **additive and reversible** — nothing existing is renamed,
dropped, retyped, or backfilled destructively. The live attendant / admin /
enforcer code paths read and write exactly the same columns they do today and are
unaffected.

---

## Design principle: keep the live 4-state column, layer the richer model on top

The live `boots.status` column stays exactly as-is:

```
booted | released | settled | completed   (CHECK-free text, default 'booted')
```

All current code (the `/api/boots` PATCH lifecycle, attendant mark-paid, history
counts, KPIs) continues to use this column unchanged.

The richer 11-stage lifecycle from your plan is expressed through a **separate,
nullable "enforcement stage" column** plus a small **audit-timeline table**. The
preview *derives* most stages from data that already exists (boot_requests,
release_requests, Stripe paid status) and only persists a stage when an enforcer
takes an action in the preview. If the stage column is NULL, the preview falls
back to deriving the stage from `status` — so existing rows "just work" with no
backfill.

### Stage ↔ live-status mapping (how the preview reads existing rows)

| Preview stage         | Derived from existing data                                              |
| --------------------- | ----------------------------------------------------------------------- |
| `draft`               | a `boot_requests` row, status `pending`, not yet initiated              |
| `review_needed`       | request flagged (paid-plate match / mismatch) — derived at read time    |
| `pending_enforcement` | `boot_requests` status `initiated` but no `boots` row yet               |
| `booted`              | `boots.status = 'booted'`                                               |
| `payment_pending`     | `boots.status = 'booted'` + enforcer marked "awaiting payment" (new col) |
| `paid`                | `boots.status IN ('settled','completed')`                               |
| `release_pending`     | open `release_requests` row (status `pending`) for the boot             |
| `released`            | `boots.status = 'released'` OR release_request `released`               |
| `completed`           | `boots.status = 'completed'`                                            |
| `cancelled`           | `boot_requests`/`release_requests` status `dismissed`                   |
| `reopened`            | `boots.status` moved back to `booted` after a resolution (new col flag) |

Only `payment_pending`, `reopened`, and explicit `review_needed` need a stored
hint — that's what the new column provides. Everything else is read-derived.

## Proposed DDL (additive only)

```sql
-- 1. Optional enforcement-stage hint on boots.
--    NULL = derive stage from status (existing rows need no backfill).
ALTER TABLE public.boots
  ADD COLUMN IF NOT EXISTS enforcement_stage text;          -- nullable, no default

-- 2. Optional structured evidence labels captured in the field.
--    JSON array of {label, photoIndex} — kept separate from the existing
--    `photos` column so the live photo array is untouched.
ALTER TABLE public.boots
  ADD COLUMN IF NOT EXISTS evidence_labels text DEFAULT '[]';

-- 3. Append-only audit timeline for enforcement actions (new table).
--    Pure addition; nothing references it except the preview.
CREATE TABLE IF NOT EXISTS public.enforcement_events (
  id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  boot_id      bigint,                 -- nullable: events can predate a boot row
  request_id   bigint,                 -- optional link to a boot_request
  stage        text NOT NULL,          -- the stage entered
  note         text,
  actor_id     bigint,
  actor_name   text,
  created_at   text NOT NULL
);

CREATE INDEX IF NOT EXISTS enforcement_events_boot_id_idx
  ON public.enforcement_events (boot_id);

-- 4. RLS policy matching the existing `boots` table (permissive anon ALL).
--    The server uses the anon role; without this, RLS (on by default) blocks it.
CREATE POLICY app_all_enforcement_events ON public.enforcement_events
  FOR ALL TO anon USING (true) WITH CHECK (true);
```

That's the complete set. No `ALTER ... TYPE`, no `DROP`, no `NOT NULL` added to
existing columns, no data rewrite.

---

## Rollback (one statement, fully clean)

```sql
DROP POLICY IF EXISTS app_all_enforcement_events ON public.enforcement_events;
DROP TABLE IF EXISTS public.enforcement_events;
ALTER TABLE public.boots DROP COLUMN IF EXISTS evidence_labels;
ALTER TABLE public.boots DROP COLUMN IF EXISTS enforcement_stage;
```

## Could we do ZERO schema changes instead?

Yes — and I want to flag it as the lower-risk option. The preview can express the
full 11-stage lifecycle **read-only-derived** from existing tables, storing the
2–3 "hint" states (payment_pending, reopened, review_needed) in **in-memory React
state during the session** instead of the DB. Downsides: those few hint states
don't survive a refresh, and there's no persisted audit timeline. But it touches
the database **not at all** — the safest possible preview.

**I recommend starting with the zero-schema version**, then applying the additive
migration above only once you've seen the preview and want the hints + audit trail
to persist. Your call.
